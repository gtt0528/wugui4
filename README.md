# 乌龟4（Cocos Creator 2.4.15 / TypeScript）

源自两广的 4 人纸牌玩法：1 个「敌人」（持方块4）+ 3 个「乌龟」互相不知道身份，
连续多局对抗、局间交牌。当前是**单机版（1 人 + 3 个 AI）**，目标是打磨好上架微信小游戏。

---

## 一、怎么跑起来

### 日常启动（推荐）

桌面双击 **「乌龟4游戏」** 快捷方式，直接打开编辑器并加载本项目。
进入编辑器后等右下角出现「编译完成」→ 按 **Ctrl + P** 预览。

> 启动场景已设为主菜单 `menu.fire`（`settings/project.json` 的 `start-scene`）。
> 想直接看牌局，就在资源管理器双击 `assets/scenes/game.fire` 再按 Ctrl+P。

### 场景结构（两个场景都已配好，不用手动摆节点）

| 场景 | 结构 | 说明 |
|---|---|---|
| `assets/scenes/menu.fire` | `Canvas → Main Camera / Menu` | 主菜单，`Menu` 节点挂了 `MenuScene` |
| `assets/scenes/game.fire` | `Canvas → Main Camera / Game` | 牌局，`Game` 节点挂了 `GameScene` |

两个场景的 Canvas 都是 **1280×720 + FitWidth/FitHeight 均勾选（SHOW_ALL）**，
Widget 已禁用（之前画面缩在左下角就是 Widget + 非 Fit 造成的，别再打开）。

> **场景切换要求**：`cc.director.loadScene('menu' / 'game')` 依赖构建列表。
> 如果运行时报「进入牌局失败」，请到 **项目 → 构建发布 → 参与构建的场景** 里把
> `menu` 和 `game` 都勾上，或直接在预览后用编辑器菜单重新构建一次。

### 万一画面只显示一小块、缩在角落

1. 确认 Canvas 组件的 `Fit Width` 和 `Fit Height` **都勾选**；
2. 确认 Canvas 上**没有启用** Widget 组件（本项目已设为 `_enabled: false`）；
3. 重开预览（Ctrl+P 关掉再开）。

## 三、已实现的规则

| 项目 | 实现 |
|---|---|
| 牌力顺序 | 方块4 < 梅花4 < 红桃4 < 黑桃4 < 方块5 … < 黑桃3 < 小王 < 大王 |
| 牌型 | 单张、对子、三张、鸡（4张同点）、三带二、顺子（5张连续）、同一花色（5张同花色，不能红黑混凑）、一条龙（5张同花色连续）、4带1 |
| **五张牌型互相可吃** | **一条龙 > 4带1 > 三带二 > 顺子 > 同一花色**（张数同为 5 张即可互压，不用同型） |
| **同一花色比大小** | **先比花色：方块 < 梅花 < 红桃 < 黑桃**；花色相同再比这五张里**最大那张的点数**（一条龙同型互压时同此规则） |
| 限制 | 2、3、大小王**不能**进顺子/一条龙；王可单出，**大王+小王放在一起算一对（能压任何对子）** |
| 发牌 | 逆时针；首局掷骰子定起点（点数最大，相同重掷）；**起点与下家 14 张，其余 13 张** |
| 身份 | 持方块4 者为「敌人」（暗）；其余 3 人为「乌龟」 |
| 首局先手 | 持梅花4 者先出 |
| **胜负（关键）** | 敌人出完牌时：<br>· 若**所有乌龟已出完** → 乌龟方赢；<br>· 若**仍有乌龟没出完** → 敌人赢，没出完的乌龟**「被抓走」**，立即结束。<br>名次只给赶在敌人出完**之前**出完的乌龟（按顺序 = 导游/中游/尾游）；被抓走的乌龟不算名次。 |
| **敌人暴露** | 一圈无人压住、轮到敌人领出、且**方块4还在敌人手上**时，敌人身份对所有人公开（UI 播报），且敌人领出**必须打出含方块4的牌型**；方块4出掉后约束自动解除。方块4已打出则不触发。 |
| 交牌时机 | 从第 2 局起，开局先交牌 |
| **交牌顺序（桌上抢牌）** | **链路 A（敌人 ↔ 游客）**<br>① 敌人**手动点选最大的 N 张**（N = 游客人数），点「交到桌上」，牌落到**桌子正中间**；系统校验必须是最大的那 N 张、且不含方块4 与本局已换过的牌<br>② **导游 → 中游 → 尾游** 依次从桌上**自己挑一张**，点「拿牌」收进手里（谁先挑谁占便宜）<br>③ 各游客各自挑一张还给敌人——**自愿选择，不必是最小的**，只排除方块4 与本局已换过的牌<br>**链路 B（敌人 ↔ 被抓龟）**<br>④ 每只被抓龟点**最大**的一张，直接落到敌人手里（不经过桌子）<br>⑤ 敌人**一次性点选 M 张小牌**（M = 被抓龟人数），点「还牌」一起摆到桌中间偏上位置（自愿选择不必最小）<br>⑥ 被抓龟按「**谁交给敌人的大牌更大，谁先挑**」的顺序，从桌上各自挑一张拿走 |
| **交牌展示** | 牌从给出方**缓慢飞出**（停留 → 弧线飞行 → 落点停留，大牌 2.4s、小牌 1.9s），给出方旁飘「交出 X」、接收方旁飘「收到 X」，桌面中央流程条写明这一步是谁给谁。**牌落到桌上后停留 1.5s** 再进入下一步，保证看清。<br>**敌人一次摆 N 张是「一组」播**（N 张同时飞落桌面、一次刷新），不是逐张串行——逐张串行时 3 张要 15.6 秒、期间桌上空白且流程不动，看起来就是「卡死」。改后 3 张约 4.9 秒 |
| 称呼 | 出完牌的乌龟按顺序叫 **导游 / 中游 / 尾游**（统称游客）；没出完被敌人抓的叫 **被抓龟**；持方块4的是 **敌人** |
| 交牌限制 | **刚换来的牌当次不能马上再换出去**（`Card.exchanged` 标记，本局内有效，下局重新发牌自动清除）；**方块4 永远不能拿去交**（身份牌），逻辑层与 UI 双重拦截 |
| **交牌后先手** | 本局所有「交出大牌」的人（敌人摆到桌上的 + 被抓龟给敌人的）里，**交出的那张牌最大者先出**——「毕竟交出最大那张牌出去的亏了一点」；牌同为最大时按座位靠前者。无人交大牌（首局）→ 持梅花4 者先出 |
| 积分 | 初始 1000，赢一局 **+15**，输一局 **-10**，最低 0；积分不足可领救济分（正式版换成看广告） |

## 四、操作说明

### 主菜单

- **开始匹配 / 创建房间**：联机功能开发中，当前点会提示「敬请期待」。
- **人机对战**：进入牌局（1 人 + 3 AI）。
- **玩法规则**：弹出图文说明。
- 左上角显示昵称、积分、战绩；积分不足时点「人机对战」会弹出领取救济分。

### 牌局内

- **点手牌**：选中/取消（选中会上抬 22px）。
- **出牌**：按已选中的牌出；不合法会提示。
- **跳过**：仅在跟牌且要不起时可用。
- **提示**：自动选中「能压过上家的最小一手」。
- 三家按钮间距 200px，`出牌 / 跳过 / 提示` 不再挤在一起。
- 每个座位旁有**信息框**：名字 + 剩余张数 +（出完后）名次标记。
  自己的信息框在左下角，右下角还有一个「剩 N 张」常驻提示。
- **一圈结束**（无人再压，回到领出者）：上一圈四家出的牌会**全部淡出清空**，然后才出下一轮。
- 左上角 `≡` 可以确认后退出本局回到主菜单。

### 交牌阶段（从第 2 局起，桌上抢牌模型）

屏幕顶部状态栏会显示当前是谁在交牌、该点什么。整个过程**全员可见**：

| 步骤 | 谁操作 | 怎么操作 |
|---|---|---|
| ① 敌人 → 桌子中间 | 敌人 | 逐张点手牌选出**最大的 N 张**（N = 游客人数，选了几张按钮上会显示 `交到桌上(2/3)`），点 **「交到桌上」**。选错了系统会提示「只能交手上最大的 N 张」 |
| ② 桌子上 → 导游 | 导游 | 桌子中间的牌会**金边浮动**，点任意一张，再点 **「拿牌」** |
| ③ 桌子上 → 中游 | 中游 | 同上，只能从**剩下**的里面挑 |
| ④ 桌子上 → 尾游 | 尾游 | 同上，最后一张没得挑，自动归他 |
| ⑤ 游客 → 敌人 | 导游/中游/尾游 | 挑一张自己觉得不好用的牌，点 **「还牌」**——**不必是最小的** |
| ⑥ 被抓龟 → 敌人 | 被抓龟 | 点最大的一张（不能点别的），点 **「交出大牌」** |
| ⑦ 敌人 → 桌子中间 | 敌人 | 逐张点手牌选出 **M 张小牌**（M = 被抓龟人数，按钮显示 `还牌(2/3)`），点 **「还牌」**，和交大牌完全一样的摆法，一起摆到桌中间偏上位置 |
| ⑧ 桌子上 → 被抓龟 | 被抓龟 | 按「**谁交给敌人的大牌更大谁先挑**」的顺序，各自点桌上一张小牌，点 **「拿牌」** |
| ⑨ 游客给回的小牌 | — | 游客 → 敌人是**一对一**的，直接落到敌人手里，**不需要挑选** |

- 手牌里**不能交的牌会压暗**（方块4、本局已经换过的牌），点了会直接告诉你原因。
- 敌人选大牌时，按钮上会实时显示已选张数，选够了才能点。
- 每一步都有动画：牌**缓慢**飞出（停留 → 弧线飞行 → 落点停留），给出方旁飘「交出 X」、
  接收方旁飘「收到 X」，桌面中央流程条写明这一步是谁给谁什么牌。
- 牌**落到桌子正中间后停留 1.5 秒**，让所有人看清桌上摆的是哪几张，然后才轮到下一位拿牌。
- 全部交完 → 播报「谁交出的牌最大，谁先出牌」，直接进入出牌阶段。

### 结算面板

- 显示本局阵营结果、四家名次、**本局积分变化**、当前总分、本局敌人是谁。
- **继续留在房间**：显示「正在等待其他玩家进入房间...」，随后开下一局（单机版 AI 自动就位）。
- **退出游戏**：回到主菜单。

## 六、平衡性实测数据（新规则：敌人出完即分胜负）

| 场景 | 敌人胜率 |
|---|---|
| 独立首局（2000 局，无交牌） | **63.5%**（敌人第一个出完率 17.7%） |
| 连续 4 局合计（1600 局） | **62.3%** |

**说明**：新规则下「敌人出完时只要还有乌龟没出完就算敌人赢」，敌人不再需要第一个出完，
所以胜率天然比旧规则（敌人必须第一个出完，约 20%）高很多。这是规则本身决定的——
如果你觉得敌人太强，可以改 `GameEngine.checkRoundEnd()`（例如只在敌人第一个出完时判赢），
改完跑 `balance.js` 看数据。

> 样本小于 400 局时波动很大，要下结论请跑满默认样本量。

## 七、常见问题

### 控制台刷一屏 `Cannot find module '../core/Card'`

完整表现大概是这样（一次刷一屏，`AI` / `Pattern` / `GameEngine` 全部报错）：

```
load script [./assets/scripts/core/Card] failed : Error: Cannot find module './assets/scripts/core/Card'
load script [../core/GameEngine] failed : Error: Cannot find module '../core/GameEngine'
load script [./Card] failed : Error: Cannot find module './Card'
...
```

**真正的原因是 Cocos 的增量编译缓存坏了，不是代码有错。**

Cocos Creator 2.4 的脚本编译器（quick-compiler）是增量的：它在
`temp/quick-scripts/src/` 里留下上次的编译结果，判断「这个文件编译过」就跳过。
如果那里**残留了 `Card.js.map` 但 `Card.js` 被删了**，编译器就认为 `Card` 已编译好、
不再生成，于是 `__quick_compile__.js` 的模块表里没有 `Card`，
`__qc_index__.js` 却仍然 `require` 它 → 一报就是连锁一大片。

**修复（一条命令）：**

```bash
rm -rf temp/quick-scripts
```

然后**在 Cocos 编辑器里重新打开工程**（关掉编辑器再开，或菜单 `开发者 → 重新加载`），
它会全量重编一次，问题消失。源码一行都不用改。

**怎么确认是这个原因**：打开 `temp/quick-scripts/src/assets/scripts/core/`，
看 `.js` 和 `.js.map` 是不是成对的。少了任何一个 `.js` 就是它。

**以后自查**（本工程已带这个脚本）：

```bash
node tools/check-scripts.js
```

它会检查三件事：源码目录有没有散落的 `.js`（Cocos 会把它们当脚本重复加载）、
`quick-scripts` 里 `.js` 与 `.js.map` 是否成对、每个 `.ts` 是否有 `.meta`。

### 为什么会出现这种缓存错乱

最典型的来源是**手动往源码目录跑过 `tsc --outDir`**。编译产物落进 `assets/scripts/` 后，
Cocos 会把它当成正式脚本一起加载，之后删掉时又容易只删 `.js` 忘了 `.js.map`，
就留下了上面那种「有 map 没 js」的半残状态。

**所以：编译输出永远指向 `temp/` 或 `.testout/`，不要落到 `assets/` 下。**

### 连点会重复搬牌 / 出现重影

**已修复，四道防线叠加：**

1. **按钮层去重**（`CardView.ts`）：一次完整触摸只认一次抬起，且两次回调间隔
   小于 `BUTTON_TAP_GAP = 0.2` 秒的直接丢弃。手机上「按一下被识别成三下」就挡在这。
2. **提交锁**（`GameScene.exchangeLock` / `playLock`）：点下提交的**同一个同步块**里
   立刻上锁并清空当前选择，第二次点击进来时既拿不到锁也拿不到旧选择。
   提交失败才解锁并还原选择，让玩家改。
3. **点击节流**（`TAP_THROTTLE = 0.18` 秒）：所有手牌、桌面牌的点击都过这道时间窗。
4. **动画防叠加**（`flyingRecord` + `clearFlyingCards` + `tableCardsSig`）：
   同一条飞牌记录不会并行播两遍；桌面牌内容没变化就不销毁重建（节点上挂着浮动
   tween，反复重建会让同一张牌瞬间出现两个节点）；清层前先把 tween 停掉，
   避免动画跑在已销毁的节点上留下残影。

回归测试见 `test/tap.test.ts`（13 项），专门模拟连点。

### 界面卡住不动了（已系统修复）

「停在这个界面不动」本质上只有一种原因：某个**状态锁**被置为 true 之后再也没复位。
这类锁一旦残留，按钮就不显示、点击也不响应，看起来就是死界面。

现在所有锁都保证「无论成功失败都会复位」，并且有看门狗做最后兜底：

| 锁 | 卡住的表现 | 现在的保证 |
|---|---|---|
| `exchangeChainAlive` | 交牌不推进 | **单链保护**：只有一条链能改写 `logPlayed`；链代号让旧链回调自动作废；看门狗 9 秒无进展强制拆链 |
| `flyingRecord` | 飞牌不再出现 | 每条记录播完**强制**置 false，且 `logPlayed` 单调前进（绝不允许原地重播） |
| `exchangeBusy` | 拿牌/还牌按钮不亮 | `finishLogChain` 复位 + 异常兜底 + 看门狗 |
| `exchangeLock` | 提交后按钮一直「处理中」 | `afterExchangeSubmit` 用 `finally` 解锁；**链推进到下一个真人步骤时（`processExchangeInner` 分支③）也强制解锁**——否则「拿牌→还牌」这种同一局里连续两个真人步骤，第二个会被上一 步的锁挡死；看门狗 2 秒兜底 |
| `playLock` | 出牌按钮永久锁死 | `onPlayClick` / `onPassClick` 全包 `try/finally` |
| `busy` | 出牌阶段不动 | AI 回调 `finally` 复位；出牌阶段看门狗 6 秒恢复 |
| `ROUND_WAIT` | 点「继续留在房间」后不再开局 | 看门狗 4 秒后自动开下一局 |
| 结算面板 | 局末无面板可点 | `safeShowResult` 一局只尝试一次，失败画最小兜底面板，再失败直接开下一局 |

**三条硬规则**（改这块代码时别破坏）：

1. **推进量必须单调递增**。任何「播完继续」的逻辑，推进量（`logPlayed`）只能变大不能原地。
   一旦允许原地，就是死循环。
2. **锁的复位放 `finally`，不放 `try` 尾部**。中间任何一步抛异常都不能让锁残留。
3. **不要指望某个定时器一定会回来**。节点会被销毁、tween 会被打断，凡是「等回调」
   的地方都要有兜底超时。

回归验证：`test/` 四个套件共 199 项全过；另有 `.testout/chain.js` 专测并发与异常注入。
**注意：仿真必须连打多局**——第 1 局没有交牌阶段（没人被抓乌龟），单局仿真测不到任何交牌锁。
`.testout/chain.js` 连打 6 局 × 60 次的对比结果：

```
修复前：60 局全部卡死（还牌 31 次 / 被抓龟挑牌 22 次 / 敌人还小牌 7 次）
修复后：60 局全部通过（含异常注入 40 局、高频并发 40 局）
```

## 九、联机与后端（开发中）

项目已从「纯单机」升级为「单机 + 联机 + 后端」结构，根目录可整体用 IDEA 打开：

```
wugui4/
├── assets/…            Cocos 客户端（现有，未动）
├── backend/            Spring Boot 3 账号/战绩服务（端口 8081）
├── gameserver/         Node.js 联机对战服（ws://localhost:8090）
├── pom.xml             Maven 聚合 pom（IDEA 打开根目录自动识别）
└── test/               单机逻辑回归测试
```

### backend（账号 / 对局记录）

- 技术栈：Spring Boot 3.3 + JPA + MySQL 8（库名 `wugui4`，密码见 `application.yml`）+ JWT（jjwt 0.12）
- 表：`t_user`（openid/昵称/累计胜负）、`t_match`（一局）、`t_match_player`（一局中每人）
- 接口：
  | 方法 | 路径 | 说明 |
  |---|---|---|
  | POST | /api/auth/guest | 游客登录（昵称），返回 JWT |
  | POST | /api/auth/wx | 微信登录（wx.login 的 code 换 openid；未配 appid 时返回 501） |
  | GET  | /api/users/me | 我的信息与累计战绩 |
  | POST | /api/matches | 上报一局（玩家本人单条；gameserver 用 X-Internal-Token 批量 4 条） |
  | GET  | /api/matches/me | 我的最近对局 |
  | GET  | /api/rank | 胜场排行榜 |

### gameserver（4 人联机对战）

- **服务器权威**：客户端只发动作，合法性由服务器的 `GameEngine.ts` 判定——联机对战服直接复用客户端的纯逻辑引擎（Card/Pattern/GameEngine/AI 原样编译进服务器），规则改一处两端同步生效。
- 冒烟测试：`gameserver/test/smoke.js` 用 4 个假客户端托管打完整局，**连跑 8 次 8/8 通过**。

### 启动步骤

```bash
# 1) 数据库（一次性）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS wugui4 DEFAULT CHARACTER SET utf8mb4"

# 2) 账号服务（需 JDK 17，IDEA 里直接跑 Wugui4Application，或：）
cd backend && mvn spring-boot:run

# 3) 对战服
cd gameserver && npm install && npm run build && npm start

# 4) 联机冒烟测试（另开终端）
cd gameserver && npm run smoke
```

### 协议摘要（gameserver）

- 客户端：`login` → `join` → `ready`（4 家都 ready 自动开局）→ `act`（auto/play/pass）→ `next`
- 服务器：`loginOk` / `roomOk` / `roundStart` / `hand`（私密手牌）/ `turn` / `played` / `state` / `roundEnd` / `error`
- 掉线重连：同 userId 重进 join 会坐回原位（牌局快照恢复开发中）
